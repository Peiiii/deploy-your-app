# 同一作品重复发布：方案比较与推荐

日期：2026-10-03（Asia/Shanghai）。范围：用户要求结合技术综合考虑、多方案比较并给出最佳建议，并补充“创建/上传页右侧展示最近应用、点击进入该应用更新界面”的想法；初始讨论交付调查结论和推荐设计；用户随后明确要求全托管落地，本文末尾记录首期实现范围与验收。完整治理路线仍是后续推荐，不冒充首期已实现。

## 问题与有效证据

用户指出很多应用打开后都叫“诡市”。当日只读生产 D1、已部署 R2 文件核对：

- 同一账号共有 29 个项目，27 个公开上线，2 个未上线；创建集中在 2026-09-25 至 09-29。
- 27 个上线项目的已部署 HTML 标题均为“诡市 - 驭鬼者社区”，平台项目名多为 x、xx、123 等。
- 27 个部署文件有 24 种字节内容；完全相同的副本分别有一组三份、一组两份，其余不同。仅用文件哈希去重，最多收拢三个额外副本，仍会有 24 条。
- 该账号有 61 次成功部署，另有失败/拒绝记录。事实证明多项目、多次部署；用户动机未经核实，不认定恶意刷屏。
- 页面直接读取返回 403；标题和字节比较来自 R2 已部署文件，不据此宣称已验证浏览器访问或完整应用功能。

## 目标与非目标

最小完整结果：作者修改已有作品时容易更新原项目、保留网址；疑似重复新建有明确反馈；确认属于同一作品的历史多个地址不重复占用公共列表；所有原链接和各自业务数据仍可用。

不保证识别所有恶意改写或跨账号刷屏；不自动合并数据库、评论、点赞、收藏、访问指标或浏览器 localStorage；不以标题、AI 描述、平台名称当唯一身份；不新增内容生成能力、向量数据库或通用作品管理平台。

## 四条可行路线

| 路线 | 实现方式 | 优点 | 缺口与代价 | 判断 |
| --- | --- | --- | --- | --- |
| A：最近应用快捷入口（用户补充） | 创建页右侧展示本人最近应用，点击进入其独立更新界面；卡片直达更新；CLI 记住 projectId | 内容上传前就提醒，用户识别自己作品，不依赖相似算法；复用部署合同，改动较小 | 最近列表不能覆盖所有旧作品；名字 x 时需缩略图/网址；单独不能收拢历史 27 条 | **最佳首期主方案**，后续加识别与展示治理 |
| B：强制内容去重 | 服务器哈希匹配后拒绝创建或自动覆盖；可扩展标题唯一 | 哈希准确、索引便宜，完全重复容易拦截 | 本案仍剩 24 种文件；同标题模板误伤；自动覆盖无法表达独立副本、不同班级或测试地址 | 哈希只作为证据，不作为自动覆盖政策 |
| C：自动相似度合并 | DOM/文本/代码签名，或 embedding/LLM 自动聚类与合并 | 能覆盖改名及近似版本，减少人工整理 | 共享模板、不同关卡和语言版本容易误判；阈值待验证；LLM 增加延迟、成本和不可重现性；不可逆合并风险大 | 不作为首版主链路；可辅助管理员找候选 |
| D：稳定项目身份＋识别提示＋确认后的展示分组 | 同一 Project 持续部署；同作者内容检查；用户/管理员确认版本关系后广场选代表 | 同时处理源头、历史与合理副本；保留链接；规则可解释；不依赖 AI | 需跨前端、CLI、Worker、D1 修改；分组和筛选语义必须统一；不能完全阻止恶意独立声明 | **最佳推荐，按必要依赖实施** |

推荐以 A 为首期主方案，按 D 完成后续有证据支持的补充，复用 B 的准确证据而不采用其强制政策。核心是稳定身份，识别只是建议，展示分组只改变公共发现，不改变运行身份。C 的模糊匹配可用于候选，不获得自动覆写、删除或隐身权限。用户补充的入口使提醒从“上传后被系统判断”前移到“上传前自己认出作品”，因此优先级高于建立相似识别体系。

## 推荐用户链路

### 正常更新

作者从“我的应用”卡片点“更新内容”，进入同一发布表单，目标项目和既有网址常显；粘贴 HTML、上传 ZIP 或选择 GitHub 来源，点击“发布更新”。沿原 DeployService、Executor 发布到该 projectId。成功反馈“已更新，网址保持不变”；失败显示原有诊断并保留输入、目标和本次请求信息，重试不新建项目。

创建/上传页保持新应用表单；桌面右侧增加“更新已有应用”区域，列最近 6 个本人应用（缩略图、名称、网址、状态/最近发布时间）与“查看全部”入口。点击其中一项进入该项目的更新界面，明确显示目标名称、原网址和“发布更新”，不能仍停在新建页面仅暗中替换 projectId。没应用时不显示空管理面板；未登录不拉私人项目；加载、失败和重试只影响右侧，不阻塞左侧上传。

手机没有右侧，入口在上传编辑器前作为紧凑“更新已有应用”区域，最近项可展开，不把提示放到长表单之后。最近未上线草稿可标记“继续发布”，区分“已上线应用的更新”；查看全部沿用我的应用列表，不一次加载所有项目。

切换前未填写内容时直接导航；已经输入 HTML/选择文件时，在同一会话内保留创建草稿，更新页可明确点“使用刚才的内容”，不自动发布、不把新应用名称/新地址覆盖到旧应用。返回创建页可恢复输入。File 保留仅对当前页面会话成立，完整刷新后须明确重新选择文件，不把无法持久化的文件当作已恢复。已有创建草稿 ID 保留，返回后重试不能再次分配。

原 `/projects/:id?tab=deployments` 已能进入更新控制区，首期优先复用并改善“更新应用”标题和上传表单，而不是新造同一功能页面。侧栏导航可直接到此地址；若未来另设 `/projects/:id/update`，仍须复用相同表单和部署执行 owner，不保留两套逻辑。当前 ProjectSettings 只在全局列表为空时补载，某个目标不在已载分页中时可能一直等待；实施入口时必须补足已有 ensureProjectLoaded 路径或直接授权详情读取，不能只验证从首屏卡片点入。

右侧复用已有 `GET /projects?scope=mine`、ProjectProvider 和 ProjectManager。不能用公共广场充当本人列表，也不能用“全局 projects 非空”证明当前账号最近列表完整。近期列表查询与全量分页列表分开表达，复用同一项目实体；请求绑定登录身份与序列，换账号/退出时清空且拒绝过期返回。缓存已有本人第一页时可先展示，再请求有界最近项；局部查询不得 setProjects 覆盖整个 dashboard 分页。首期可复用列表接口现有最近排序，不新增最近应用专用后端或向量查询。

### 从新建入口上传了已有作品

HTML 在创建草稿前向服务器检查本人已有成功发布内容；同源/同标题且相近的候选显示作品名、缩略图、网址、最近成功时间、匹配原因，不把平台名 x 当作唯一线索。

提示选项：“更新原应用”（突出）、“另存一个版本”（独立网址但归入同一展示组）、“作为独立作品发布”（有意独立）。更新必须由用户点选目标，服务端再次校验归属；另存版本说明广场默认显示代表版本。只有存在候选才出现这些选项。

检查中不创建草稿、不开始构建；请求失败可重试，也可明确继续新建，不静默把失败当作未发现重复。候选消失或目标被删除时保留输入，请用户重新选择。网络重试与内容编辑使用不同请求语义，过期检测结果不能覆盖新内容候选。

### CLI 连续发布

初次发布保存目标 projectId；同目录、同 API origin、同账号再次 deploy 默认更新。`--project <id>` 明确目标，`--new` 明确新建；这些是拟新增能力。更换账号、站点、绑定项目不存在或无权限时停止并说明，不偷偷创建替代项目。非交互运行遇到多个候选要求显式指定，避免挂起询问或自动覆盖。

绑定是本地部署状态，不放入公开内容 manifest；不保存登录 cookie。按 origin、当前账号和规范化 manifest 路径隔离，首次分配草稿后立即原子保存，上传/构建失败重试复用；取消尚未发出的新建操作不影响已有绑定。跨机器没有本地绑定时可以用 --project；不能仅凭公开 slug 接管项目。

## 内容识别：先确定性证据，后验证近似规则

1. **只查本人。** 跨作者共同模板不作为“你已发布过”的证据，也不泄露私有应用存在。
2. **服务器算特征。** 浏览器可以即时解析标题辅助交互；匹配证据不能相信客户端自报 hash、owner 或匹配结果。
3. **HTML：** 保留原始 UTF-8 内容 SHA-256；另存标题规范值和有界正文/DOM 特征。原始哈希相同代表输入相同，不代表应覆盖项目。标题相同、DOM 结构近似都仅产生候选；仅 JS 改变但正文相同仍可提示，不能认定同一业务功能。
4. **来源差异：** GitHub 可用规范化仓库＋branch/subpath 作为来源候选，仍允许一个仓库多个作品；ZIP 的文件名和压缩字节哈希不能代表应用身份。目录指纹应对允许发布的规范相对路径及逐文件内容哈希排序计算，不能忽略运行相关文件，更不能在 Worker 内解压 75 MB ZIP。
5. **首版识别边界：** 本案 HTML 的发布前检测纳入首版；所有来源都提供显式更新，GitHub 有来源提示。ZIP 在选择目标前不增加 owner 级上传会话或双重上传，只使用已有项目更新及已知信息提示；目录级近似检测须在现有 Node 源处理 owner 取证后另行设计。不得宣传所有 ZIP 的发布前内容去重已经覆盖。
6. **成本：** 精确 hash 在 D1 用 owner/hash 索引；近似只对同作者有界候选比较，generic title（如 game/index/无标题）不能单独提高置信度。不抓网页、不在广场请求里读取 R2 或调用 AI。特征缺失时显式无法判断，保持正常发布。
7. **阈值：** 不把任意“相似度 90%”冻结为正确值。用本案 24 个改动版本、同作者同模板不同作品、少量文本/纯脚本应用、改名、只改脚本的样本验证召回和误提示；首版近似识别始终提示、不自动处理，精确与同标题可先独立提供可解释候选。

当前生产 projects.html_content 在本案为空；特征回填不能只扫此字段。线上 Gateway 会重写运行资源和图标，不能对抓取响应做长期指纹。新发布从原输入计算；历史可从 R2 活动指针读取实际文件，标记 feature provenance=deployed-artifact，与 raw-input 分开比较，避免把不同算法/来源 hash 视为可直接相等。

## 最小状态与权威 owner

不引入独立 Work 实体重新管理所有项目。Project 继续拥有运行身份、地址、来源、权限和部署历史；DeploymentAttempt 继续拥有一次执行及其幂等。

拟新增状态，细节在实施设计时按实际 SQL 固化：

| 状态 | 必要用途与约束 |
| --- | --- |
| 创建请求键 | 按 owner＋request key 唯一，同一新建请求重放返回原草稿；同 key 不同创建参数可恢复 409。旧调用方无 key 仍能调用，但不宣称获得新增创建幂等。 |
| 内容特征 | owner、project、成功 deploymentId、algorithmVersion、provenance、hash、titleKey、有界相似特征；匹配范围与授权在 Worker。attempt 保留本次特征，成功且仍是当前作业时更新项目匹配投影。失败输入不代替已上线作品。 |
| 展示组 | `project_discovery_groups(id, owner_id, preferred_project_id, ...)` 与 projects 可空 group_id；只在本人另存版本或管理员确认历史关系时创建。普通项目不需要额外 group 记录。 |

创建请求键在既有 ProjectService/Repository 原子处理，不加第二个项目创建 service。内容检查的业务规则归 Worker，前端/CLI 只提供内容和用户选择；Node 提供自己实际拥有的目录事实，不自行决定作品归属。展示组变更、成员同 owner 校验和代表选取归 Project/Explore 的服务器路径，前端不再自行分组。

内容投影与代表关系分开：hash/标题变化不自动拆组、并组或移动代表；修改代码仍是同一 Project。按成功作业 ID 条件更新特征，处理乱序完成与重放；fingerprint 写失败不把已经成功的网站判为失败，记录为待补偿，读取原状态并用相同作业幂等补写。实现前须沿现有 reconcile/status owner 固化补偿及其真实入口。

展示组成员和 preferred_project_id 在同一原子写边界校验，组内必须同 owner，代表必须是成员。退出分组、改代表、删除/恢复成员均有可恢复操作。空组可回收；分组不拥有应用生命周期，不允许链式指向另一个代表组。

## 广场、搜索与统计

候选先满足现有公开条件（Live、未删除、有 URL），每组确定一个有效代表：优先用户/管理员选定且有效的成员，否则按 last_success_at DESC、id ASC 选择有效成员；普通未分组项目直接成为代表。这里沿用现有公开条件，因此更新过程状态导致的短暂代表切换仍可能发生；本任务不暗中改部署可用性模型。

**顺序固定：有效成员 → 每组代表 → 搜索/分类/语言筛选 → 排序 → COUNT 与 LIMIT/OFFSET。** 搜索只返回代表，不让不同关键词把同组多个版本重新推入广场。语言目录从同一代表集合产生，再按现有目录合同忽略所选语言条件。私有、已删除、未上线版本不能作为 fallback，也不能在公开响应里泄露组成员信息。

`queryExplorePage` 的总数、页数据、语言目录复用同一 SQL 代表集合，D1 内完成；首版可用窗口函数/CTE，需用真实 D1 EXPLAIN 和当前规模数据验证，不能据理论宣称没有性能成本。不得恢复全量返回 Worker 排序、逐条查 R2 或前端页内过滤。

热度、点赞、收藏、评论继续按代表 Project 的现有统计展示与操作，不求和凑“作品总量”。历史成员的原指标不丢失、不迁移；私有成员不得参与公共热度。首页、广场、公共搜索使用同一代表查询规则；我的应用仍可看到自己的全部项目与组关系，原项目详情和直达网址照常访问。

## 现有“诡市”怎么处理

管理员先看到只读候选报告，核对同作者、标题、部署内容变化和原地址；选一个有效主版本，将已确认属于同一作品的项目加入展示组。不能根据最新时间直接认定“最好版本”，也不能把帐号的 29 个项目一概合并：2 个未上线项目和任何无证据成员单独保留。

管理员操作需明确权限、预览受影响项目及公共代表，写入可回退的成员/代表变更记录；不删除 R2、不改 slug、不重定向、不改私有性、不迁移 Cloud DB。撤销分组可恢复列表。应用中 localStorage/sessionStorage 是按 origin 隔离的；重定向到新域名会改变用户数据可见性，因此历史整理仅作用于发现列表。

## 验收与落地顺序

路线 D 风险 L3（跨入口、持久化与展示语义）；实现发布另走 L4 合同。本设计为推荐范围，不冒充已实现、已测性能或用户已确认。

1. **先交付最近应用侧栏与明确更新链路。** 创建页右侧最近项、手机编辑器前入口、点击转入原项目更新界面、保留创建页草稿及显式导入；卡片也可直达更新。补足分页目标/深链接加载与身份切换，复用全部已有来源，不依赖新指纹/展示组才能上线。本批独立验收“从创建页发现旧应用并更新、项目数不增加”。
