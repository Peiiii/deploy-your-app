# GemiGo：作品收费与作者收入分成

日期：2026-10-03（Asia/Shanghai）
状态：初步技术设计；经营主体、首批交易地区、作者准入与商品合同未确认，未达到实现就绪条件。当前交付仅为思路记录与设计调查，不开通商户、不接收真钱、不修改生产系统。
来源：[用户提出的收入激励闭环](../thoughts/2026-10-03-creator-inspiration-and-distribution.thought.md#用户新增思路作者收入驱动创作与主动传播)。定位边界沿用[产品背景](../thoughts/2026-10-03-app-deployment-direction.thought.md)，支付研究沿用[商业研究](../thoughts/2026-10-03-related-products-commercial-research.thought.md#国内经营者的跨境收款与平台交易)。本文推荐项均为 AI 建议，未选定价格、分成比例、题材或创作者人群。

## 要交付给用户的结果

作者从作品管理进入销售设置，发布有明确购买范围的作品，分享作品页；消费者先体验，再购买，随后能持续找回所购内容；作者能查到销售、费用、退款和结算，最终实际收到应得收入。平台能核对每笔交易产生的收入与成本。

本设计将“收费”分成四件相互连接的事：消费者支付、购买权益交付、作者与平台收入归属、资金实际结算。它们由不同状态证明；订单显示已付款不等于作者已到账，页面跳转成功不等于已付款。

## 收费模型的真实分叉

| 候选 | 消费者买什么 | 技术差异 | 当前建议 |
| --- | --- | --- | --- |
| 单作品或内容包一次购买 | 明确内容范围内的在线使用权 | 一次支付与购买权益；仍要定义使用期限、版本和更新范围 | 首版优先研究，最容易限定完整交付 |
| 按作品订阅 | 在有效期内持续使用 | 续费、失败重试、取消、到期、退款与权益生命周期 | 有持续价值与重复使用证据后选择 |
| AI 应用用量收费 | 次数、额度或实际使用 | 服务端鉴权、额度预占与结算、失败回补、重试幂等和模型成本 | 有具体 AI 调用任务与可控成本后选择 |

AI 建议用第一种走通首笔交易，不代表用户已确认。完整 AI 开发环境不是首笔内容销售的技术前提；可先用已有外部创作与 GemiGo 部署，之后按实际障碍补充创作基础设施。若首批商品依赖实时 AI 能力，静态作品购买方案不能代替 AI 服务端计费设计。

## 一次购买的用户链路（候选）

1. 作者在现有作品管理中进入拟新增的“销售设置”：确认收款入驻状态，填写介绍、价格、购买范围与期限，绑定公开试玩和独立受保护完整版。入驻待审或交付包未准备好时显示具体原因，不启用购买。
2. 作者分享拟新增的作品销售页。消费者无需先注册即可看介绍与试玩；购买前用平台已有账号登录，避免支付后无法绑定购买者。
3. 消费者确认商品、作者、金额和权益范围，进入支付服务商收银台。取消支付可回作品页；订单待支付不发权限。
4. 付款后返回订单页。后台尚在确认时显示“正在确认付款”，通过查单恢复，不要求重复付款；确认成功后显示“已购买，进入完整版”。关掉支付页面也应由后台完成交付。
5. 消费者以后从拟新增“已购作品”进入，换设备登录同一个平台账号仍可找回；找回购买记录不自动意味着作品具有跨设备学习进度。
6. 作者从拟新增销售面板查看每单收入和结算状态：销售额、退款、费用、作者份额、平台份额、待结算、渠道已结算及可核对的到账结果。无法确认银行或支付账户到账时，不展示为已到账。
7. 退款或争议由拟新增订单管理入口发起并显示进度，使用服务商确认结果更新账目与权益。商品下架停止新销售；已购用户如何继续使用依销售时合同处理。

这些入口目前均未实现。首版默认、空、加载与错误态应围绕上述动作设计；仅有第三方付款按钮不能交付这条链路。

## 唯一状态 owner 与交易处理

建议将交易业务放在现有 API Worker 的服务/仓库分层，持久化优先评估现有 D1，静态付费文件交付放在 R2 网关；支付服务商处理外部交易与分账/结算。具体表和 API 命名在选定商品与渠道后冻结，不预建通用计费平台。

| 状态 | 权威来源与职责 |
| --- | --- |
| 商品 | GemiGo API 保存作者、稳定项目关联、价格、币种、权益范围、交付版本/更新政策、分成与费用规则版本 |
| 订单 | API 创建；保存购买者与商品合同快照，以及唯一服务商订单/支付 ID。前端仅提交商品标识，不能决定金额或收款作者 |
| 付款、退款、争议 | 服务商为外部事实源；API 验签、核对并保存事件处理记录。不同事实分别记录，不靠单个 paid 布尔值涵盖全过程 |
| 购买权益 | GemiGo API 根据确认交易维护账号与商品权限，网关检查后交付；前端变量或 localStorage 不拥有权限 |
| 作者/平台收入 | API 保存每单收入归属、实际费用及冲正记录，由其计算可结算金额；与服务商账单对账，不再维护可任意修改的平行余额 |
| 分账与到账 | 服务商 transfer/分账/提现结果为外部事实源；API 映射和核对。提交分账请求不等于资金到账 |

建议处理链：创建本地订单 → 幂等创建渠道支付 → 服务商确认 → 幂等记录付款、权益与收入 → 查询订单并交付 → 按渠道约定分账/结算 → 对账。

- API 核验原始请求签名，核对商户环境、渠道支付 ID、订单关联、金额、币种与最终支付状态。成功返回页只能触发后台查单，不能自行发权益。[官方交付机制参考](https://docs.stripe.com/checkout/fulfillment.md?payment-ui=stripe-hosted)
- 渠道调用超时可能已经成功；用稳定幂等键及查询恢复，不能直接创建第二笔支付或分账。
- 事件接收/处理状态、渠道支付 ID 和收入入账键需有数据库唯一约束。不同事件 ID 对应同一笔支付，也只能产生一次入账和一次相应权益效果。
- 付款记录、收入记录与权益状态须以事务性提交或可恢复的持久任务协调。保存原始事件后若处理失败，应保留可重试状态；不能因已保存事件便跳过未完成的交付。并发、乱序和晚到成功事件应查询渠道真实状态后推进，不能让旧成功事件覆盖已确认退款。
- 定期核对未决付款、退款与结算，支持事件丢失后的查单修复。先证明 D1 的所需原子性和约束可承载再冻结事务实现；本次未运行数据库实验。

## 对任意 HTML 的付费交付

建议优先采用“公开试玩 + 独立受保护完整版”，降低作者改造负担。另一个可行候选是 SDK 配合受保护接口逐步加载付费内容，适合需要精细关卡/功能解锁的应用，但作者要主动集成。不能自动分析任意 HTML，把若干关卡可靠切成付费区。

受保护交付的必要边界：

- 付费包从首次上传起进入私有命名空间，使用独立销售部署映射，禁止被公开试玩的部署指针、封面服务或旧版本回退引用。不能直接把公开完整版的一条入口加锁后视为已保护；已经下载的公开内容无法追回。
- 网关在读取文件、命中缓存、返回 HEAD/304、SPA fallback、上个版本资源之前先核验当前商品的权限。HTML、JS、素材、源码映射、历史文件及所有替代域名/直链均纳入检查；付费命名空间不可通过公共资产路径访问。
- 平台账号在平台域名完成购买；应用是作者提供的不可信内容，不得获得平台登录 Cookie 或其它作品的权限。候选为应用域名专用 HttpOnly/Secure、host-only 短期访问会话，绑定商品和应用，由平台登录后进行受约束的会话交接。一次性交接码、state/PKCE、重定向白名单、跨域与重放策略须在实现前具体冻结；不在 URL 或 HTML 中传长效平台令牌。
- 首版建议每次受保护请求读取当前授权判定，不缓存授权结果；文件内容缓存可复用，但权限判断不能跳过。浏览器返回 private/no-store，拒绝响应不进入公共缓存；授权服务不可用时拒绝付费内容并提供可恢复提示。
- 服务端能阻止未购买者直接访问，无法阻止已购买者复制已收到的静态内容。退款后的权限回收针对后续服务端请求，不能撤回已经交付的文件。

公共作品维持现有免费交付路径，保护分支只适用于主动加入销售流程的商品。是否允许现有公开作品转为付费及如何处理历史用户，仍需单独决定。

## 分成账目与真钱结算

订单创建时保存收入规则快照：分成比例、分成基数、支付费用归属、退款与争议费用承担、币种与舍入。比例尚未决定；以前的 80/20 仅是金额示例。

记账用币种最小单位整数，明确舍入余数归属。展示订单金额、作者归属与平台归属，不把平台份额称为净利润；托管、AI、客服与获客成本另计。真实手续费晚于付款确定时，记录费用调整，不悄悄改写历史交易。

退款/拒付需保存冲正并调整权益。未结算收入扣减；已分账款项按渠道支持执行回退、准备金或之后结算抵扣，并明确谁承担不可追回部分。允许的部分退款不能被假装成全额退款；首版是否支持部分退款及它对购买权益的影响必须在上线前确定。

建议使用获准的平台支付产品，让作者通过服务商入驻，再由服务商按选定模式分账或结算。候选也包括真实的联合制作/授权销售关系下平台销售合作产品，但那会改变商品提供者和责任，不能靠改名规避 marketplace 准入。普通平台账户先收所有钱、之后自行转给开放作者，不作为默认设计。

## 实现前的验收合同候选

以下为后续实施需证明的链路，本次没有执行这些测试：

1. 作者完成真实入驻并发布销售作品，消费者从作者分享页试玩、登录并购买，关闭支付页后仍获交付，换设备从已购作品进入；真实订单、金额和收入归属可核对。
2. 未购用户访问完整版、资源直链、旧版、另一域名、HEAD/304 和已预热缓存均不可获得付费内容；合法购买者可用，另一商品权限不可通用；退款后未来请求被拒绝。
3. 同一回调重放、不同事件指向同一支付、并发处理、支付晚到、创建支付超时与处理崩溃均能恢复，且无重复扣款、授权或入账；退款乱序不会被旧成功事件复活。
4. 作者结算失败可查询恢复，超时重试不重复打款，真实渠道账单、退款/费用及实际收款记录与平台账目一致；沙盒流程不能代替真金结算验证。
5. 作者下架或更新作品后，历史购买范围和后续访问符合订单合同；平台免费作品与已有 SDK 登录路径不退化。

商业实验另行观察：真实购买、退款、作者收入后的再次推广/更新，以及成本后的平台收益。技术验收成功不能证明增长闭环成立。

## 冻结前需要解决的选择

- 平台当前可用的经营主体与商户账户；首批作者和消费者地区、支付准入结果。
- 首批商品卖内容访问、持续订阅还是 AI 用量；期限、版本、更新、退款及下架后的交付约定。
- 分成比例、费用与损失承担、结算周期；定价不能先于成本与购买价值验证。
- 私有部署、稳定商品/项目映射及跨域会话交接的具体协议；按选定渠道完成数据结构、状态迁移与恢复细节。
