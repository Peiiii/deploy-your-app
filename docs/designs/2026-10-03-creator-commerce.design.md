# GemiGo：先前作品销售方案已撤回

日期：2026-10-03（Asia/Shanghai）
状态：已撤回，不作为后续实现依据。用户纠正了将其需求解释为“作者发布商品、平台销售作品”的前提；本文件保留历史入口，先前正文可从 Git 历史查看。

## 撤回原因与当前范围

用户原始思路是：降低 AI 应用开发门槛，提供让创作者获得收入的机制，平台参与分成，进而激励作者主动宣传。用户要求先结合 GemiGo 当前应用形态，研究通常可以采用哪些变现方式和收费模式。

AI 上一轮过早推荐“发布商品、一次购买作品、公开试玩与受保护完整版”，并围绕该假设展开技术设计。用户明确指出该理解偏离项目。该销售路径、商品管理、独立销售页、已购作品和私有完整版部署不再作为默认方案；分成目标和降低开发门槛的思路仍保留。

后续讨论依据由[应用变现与收费模式探索](../thoughts/2026-10-03-app-monetization-models.thought.md)保存：应用继续发布、运行和分享，按使用场景研究广告、打赏、付费功能、订阅、按量服务与赞助等收入机制。新模式尚未形成稳定设计，不将探索文档当作执行计划。

## 仍可复用的调查事实

2026-10-03 定向读取[API 路由](../../workers/api/src/routes.ts)、[SDK 认证](../../workers/api/src/services/sdk-auth.service.ts)与[R2 网关](../../workers/r2-gateway/worker.ts)，观察到平台身份、应用身份和静态交付基础；在已检查的 API 源码、迁移和网关范围未发现完整应用变现链路。它们不自动证明付费功能、广告分润或按量计费已经支持。

收入需要可归属到作者和应用，并区分预估、确认、可结算及实际到账；直接付款需核实服务端结果、处理重复通知与退款；广告分成需核对广告渠道收入。不同模式的收入来源、接入和结算结构分别调查，不沿用作品销售的统一假设。

收款主体、地区与渠道准入会影响后续接入，但当前首先要选择匹配应用使用方式的变现模式。新的正式技术设计在该选择明确后建立。
