## 最小完整使用链路

**作者：**从现有应用管理进入作品设置中的拟新增“点数与收益”页签，启用变现，设置收费项的名称、说明、点数、类型与权益范围，取得稳定收费项 ID。复制 SDK 示例或创作提示词，将调用放在自己选择的按钮、玩法或任务节点，重新部署，使用测试钱包完成自验，再申请真钱模式。价格变更生成新版本，不改变正在确认的消费。

**使用者：**打开作者分享的原应用链接，免费功能照常运行；点击收费功能时，应用调用 SDK，平台打开 gemigo.io 的消费窗口。用户看到真实应用、作者、用途、扣点数和消费后余额，登录并确认。余额不足可在窗口进入充值，成功后回原待确认消费，由用户再次确认；充值本身不自动消费。确认前取消、关窗或意图过期不扣点；确认后关窗不能撤销已经提交的交易，返回应用时查询原收据恢复。

确认后平台产生可查询收据与相应权限/额度；SDK 返回交易 ID，应用按自己的逻辑继续。刷新或换设备登录后，已解锁权益可恢复；付费服务仍在执行时，用户看到任务状态并能继续查询，不能被要求重复购买。消费者在拟新增 `/wallet` 查看余额、充值、消费与退款；每条消费可回到对应应用。

**作者收益：**同一作品设置页签展示消费点数、对应实付金额、费用/服务成本、作者份额、平台份额、退款和可结算状态。实际到账由支付渠道或可核对付款凭证证明；测试收入明确标为测试，不进入真实结算。

## 收费项与权益模型

点数价格由作者设置，消费时机由作者代码控制；规则由平台后台保存，应用只能传收费项 ID、业务请求 ID 和受约束参数，不能自行指定最终价格、付款账号、收入接收者或余额。

| 类型 | 语义 | 交付方式与例子 |
| --- | --- | --- |
| repeatable | 同一能力可重复消费，每次具有独立消费意图 | 平台授予应用内额度/消耗项，或执行已登记的后台服务；道具、一次处理、一次生成 |
| durable | 同一账号一次解锁，持续有效 | 平台保存权益；拓展玩法、编辑功能。已拥有时返回原权益，不重复扣点 |
| term | 一次消费获得明确期限内的权益 | 例如应用 30 天会员；重复购买是否延长须在收费项合同中说明，本方案采用从 max(当前到期时间, 当前时间) 延长固定时长 |

订阅是 term 的持续续费约定：用户在平台窗口另行授权，保存收费项/价格版本、周期、下一次续费时间与可撤销状态。按期只消费一次，不允许作者在网页里任意循环扣钱。首版执行顺序先验证手动购买按期权益，再接自动续费；自动续费仍纳入推荐目标，不把手动购买称为已经支持订阅。

落地按上线批次控制范围：首批验证 repeatable + durable、统一钱包、作者收益与获准的真实充值/结算，以两个非 AI 试点证明闭环；第二批增加 term 与授权续费，受控 AI 服务可独立推进。首批不依赖自动续费或 AI 完成，渠道调查从开始就推进。若首个获准付费试点必须依赖 AI，则调整批次并先完成服务交付合同，不用前端自报成功代替。

用户取消续费保留已付有效期；余额不足不透支，当前到期后停止权益，提示用户充值并主动恢复，不在后来充值时追扣已错过周期。续费价格调整须重新授权；首版无复杂试用转收费或自动升级套餐。

## 方案比较与选择

| 方案 | 价值 | 代价 | 决定 |
| --- | --- | --- | --- |
| 任意应用凭 SDK 令牌直接扣全局余额 | 接入短 | 作者前端可静默扣款，现有 appId 与来源绑定不足，无法形成可信确认 | 不采用 |
| 每应用独立充值和支付账号 | 局部实现较直接 | 无法实现用户要求的统一点数，用户每换应用都重新付款 | 不采用 |

- [平台 API](../../workers/api/src/routes.ts)和[认证](../../workers/api/src/repositories/auth.repository.ts)拥有账号与会话；钱包绑定现有 user.id，不另建消费者账号。
- [作品仓库](../../workers/api/src/repositories/project.repository.ts)拥有稳定 project.id、owner_id、当前部署地址；收费项绑定稳定项目 ID，变更子域不得丢失权益或改变历史收入接收者。
- [SDK 身份](../../workers/api/src/repositories/sdk-auth.repository.ts)拥有 appId 与 appUserId 到平台用户的映射；[SDK 登录](../../packages/app-sdk/src/web/auth.ts)默认用子域推导 appId，也允许指定。现有[授权窗口](../../frontend/src/features/sdk-auth/pages/sdk-auth-broker.tsx)只检查回传域属于 gemigo.app/本地，未绑定到同一作品；新增财务路径不能把这当作已验证的项目身份。
- [云服务](../../workers/api/src/services/sdk-cloud.service.ts)有身份隔离与应用存储；通用可写云数据不拥有点数或权益，财务表不暴露给 cloud.db/kv。
- [项目设置](../../frontend/src/features/project-settings/pages/project-settings.tsx)与[SDK 结构](../../packages/app-sdk/src/apis/index.ts)是新增作者入口、SDK 的最近 owner。
- [R2 网关](../../workers/r2-gateway/worker.ts)当前交付公开应用；付费服务或私有资源要在后台鉴权，不能仅隐藏前端按钮。首版不把整个应用设为付费文件包。
- [默认 SDK AI](../../packages/app-sdk/src/apis/index.ts)是 stub；现有[OpenAI 代理](../../workers/openai-gateway-worker/src/lib/handlers/chatCompletions.ts)及[GenAI 代理](../../workers/genai-proxy-worker/src/lib/handlers/generateContent.ts)具备上游调用，但已读处理路径未见点数账目或按消费任务鉴权。不能直接将它们认作计费执行层。

新增业务沿现有 API controller/service/repository 分层，使用同一 PROJECTS_DB 中的财务迁移；无需先引入微服务、通用作者代码执行沙箱、动态支付插件或第二套身份体系。平台受控服务与数字权益覆盖首批消费者，之后才按证据扩大。

## SDK 与消费协议

拟新增 `gemigo.points` 浏览器接入，接口尚未实现：

```ts
const result = await gemigo.points.purchase({
  itemId: 'expand-levels',
  requestId: stableRequestId,
});
// granted：平台已保存权限/额度；应用读取并呈现自己的能力
// pending：查询同一笔消费/任务；不要创建第二次消费
// cancelled：返回免费体验，不扣点
```

配套只保留已存在的消费者需要的接口：查询收费项、purchase、查询收据/权益、核销已购应用内额度。SDK 不提供 arbitraryAmount、直接修改全局余额、作者端 confirm/refund 或前端自行标记服务成功的能力。requestId 对同一次点击及网络恢复保持稳定；新一次消费产生新 ID，幂等复用但参数不同则拒绝。

收费项可在用户点击前读取并展示价格，确认窗口再次以后台快照核对。默认每次消费确认；订阅使用单独明确的周期授权。高频应用可研究有额度/期限限制的事先授权，但本方案不提供无限额静默扣款。

消费窗口 `/points/confirm` 复用现有平台登录，持有短期单次 intent：绑定平台购买者、稳定项目、收费项版本、金额、请求 ID、合法 openerOrigin、随机 state 与到期时间。主域账户和 SDK appUserId 的映射必须一致，换号时要求返回应用重新登录，不能扣另一个账号的钱。

origin 必须和后台已验证项目当前部署 origin 一致，不能只信任传入 appId 或 gemigo.app 后缀。首批生产接入是现有托管浏览器应用；本地只允许隔离测试，其它宿主未经验证返回不支持，不假装自动支持。域名改动后新意图只接受当前域，已完成收据仍按稳定项目找回。

postMessage 校验平台 origin、event.source、state 与 intent；仅回传应用范围的收据 ID/状态，不传平台 Cookie 或全局账户令牌。回传不是财务事实源，应用再从后台查询。服务端确认 mutation 核验平台 session、CSRF/Origin、用户、intent 的唯一使用及合同快照。弹窗阻止、移动浏览器无 opener 时使用同一平台确认页和限定原应用回跳，SDK 回来按已保存请求 ID 恢复；用户拒绝/关闭不改变已提交交易事实。

## 账目与数据不变量

财务服务为统一 owner，维护以下必要记录（精确 SQL 在执行第一个部分形成并测试）：

| 记录 | 最小字段与职责 |
| --- | --- |
| 收费项 | itemId、projectId、authorId、type、pricePoints、说明、权益键/时长、交付模式、启停及合同版本；作者校验 owner_id |
| 钱包与入账来源 | userId、环境、可用/预留点数；充值批次的支付 ID、点数、对应实付最小货币单位、币种、未消费部分和来源类型 |
| 财务流水 | 唯一业务键、充值/预留/扣点/释放/退款、点数变动与来源批次；只追加与冲正，可用余额是同事务维护的汇总，不是另一个可手改真相 |
| 消费/收据 | requestId、user/app 绑定、收费项与作者/价格/权益/分成快照、生命周期、扣点来源分配、对应任务与原交易 |
| 权益/应用内额度 | 平台 userId + 稳定项目 + 权益键、期限/剩余次数、来源收据；平台控制写入，应用只能读或在本应用核销额度 |
| 服务任务 | 固定 jobId、收费项受控服务、预留点数、执行状态、结果引用、上游调用关联与成本；恢复不创建新消费 |
| 作者收入/结算 | 原收据、结算币种、收入/成本/份额与冲正、结算批次和渠道结果；只读汇总由这些记录计算 |
| 续费约定 | 用户与 app/item、已授权版本/周期/价格、nextDueAt、取消状态；每个订阅周期唯一扣款键 |

点数和金额都用整数；点数首版统一命名“GemiGo 点数”，用户不需要每应用再次兑换。消费者充值点数与作者可结算现金分开，充值不是作者收入；消费后按来源批次的实付价值核算。首个真钱批次建议标准充值比例、单一结算币种，不做折扣套餐；比例与币种待渠道确定，不能把示例当成承诺。

建议不提供用户间转点、消费者现金兑换、作者自行发全平台点数。免费测试点只存在隔离测试环境，不兑作者现金；生产赠送点若引入，必须明确补贴预算与作者收益规则。作者自购和测试不计可结算收入，减少循环消费套利；不是把赠送点按标准售价创造现金负债。

所有扣点采用余额/状态条件写入、唯一约束和 D1 batch 原子事务，扣点、来源分配、收据及即时权益授予必须共同成功。durable 同一用户/项目/权益键的并发购买只可成功授予一次；term 延长与扣点同事务完成。D1 batch 会在语句出错时回滚，但 UPDATE 零行不是错误；必须通过条件状态链或数据库断言防止“没扣到余额却发了权益”。[D1 官方合同](https://developers.cloudflare.com/d1/worker-api/d1-database/)

钱包写和消费后的查询走主库或 D1 一致性会话，不依赖可能过期的副本。网络重试取同笔记录，旧状态不能覆盖已确认退款；余额不为负，不允许根据客户端本地余额进行先读后写扣点。

## 扣点、交付与失败恢复

**平台授予权益/额度：**确认时原子扣点并记录 grant；提交即完成平台交付。作者的前端后续呈现可以重试，不能因为关窗或丢失 JS 回调自动再扣款。消费者可从消费记录重新进入，应用查询恢复。纯前端道具/玩法存在被修改客户端绕过的边界，不能宣传绝对保护；真正需保护的数据、资源和计算需由可信后台检查权益。

**服务消费：**确认时预留点数并持久化 job → 后台执行固定允许的服务 → 保存结果并一次性结算扣点/作者收入；明确失败释放预留，不计作者收入。超时或进程中断状态记 unknown/pending：先按上游请求标识查询，不能盲目再次调用造成重复成本。上游没有幂等/结果查询能力时，不自动重试不确定调用，保留运维核查路径；服务返回成功须是可恢复结果已持久化，不能只看 HTTP 200。

应用自定义“什么时候发起”不会变成它可伪造后台完成。消费型道具先获得平台库存再核销一次；自有后端交付后续需要具体验证协议，本方案不开放任意 URL 回调执行或允许浏览器无限退款。失败回补只能由可信任务状态或平台退款流程决定。

AI 首批建议固定一个受控、非流式、输入/输出有上限的服务，用稳定 jobId 和成本预算验证整条链路。复用已有代理的转换/上游调用代码时，计费调用入口必须在服务端验证 job；不能留同一付费服务的绕过入口，也不能未经调查就关闭其它应用正在依赖的免费代理。具体首作、模型、成本上限与上游重试合同在开始服务部分前冻结。

退款关联原消费并按其来源恢复点数、冲正收入和撤销对应权益，不能任意充值造点；已核销额度或已交付服务的退款由平台规则处理。渠道充值退款/拒付追回来源批次，已消费导致的权益、作者收入与欠款进入核对，冻结受影响可结算金额，不让钱包无限负值。上述处理不能等到上线后补齐。

## 真钱充值、分成与渠道门

用户支付 → 验签并核对后台订单、金额、币种、最终状态 → 幂等入账点数。支付回跳只能查单，关闭页面仍由 webhook/对账恢复入账。作者结算按消费关联的确认收入，明确支付费、平台服务/AI 成本与作者分成的分配基数；费率、结算周期与退款准备尚需实际成本与渠道合同，作者开通真钱前必须展示。

支付选型必须描述完整业务：“平台统一充值点数、跨应用使用、第三方作者获得收入与结算”，普通商品付款或普通分账支持不能直接证明适用。2026-10-04 查阅 [Stripe 限制业务规则](https://stripe.com/legal/restricted-businesses)，其中 credits/stored value、创作者平台及支付聚合存在专门审核边界；本方案不据此断定批准或拒绝。Creem 合作分成的 marketplace 限制继续沿用[既有研究](../thoughts/2026-10-03-related-products-commercial-research.thought.md)。

当前未收到经营主体/商户账户信息。下一步据主体、首批作者及消费者地区选择唯一渠道并核实该交易模式；不同时实现多支付适配器。测试环境可以验证机制，但不作为真钱充值、实际分成或银行到账验收。真实上线前必须冻结充值比例、作者净收入规则、结算周期、退款规则及服务商实际批准；无需因此停止平台内可独立设计和验证的部分。

## 验收与实施门

后续产品验收链路候选：

1. 作者在真实作品设置登记收费项，应用按钮触发消费；消费者在统一钱包充值后，分别在两个应用消费，得到各自权益，同一余额及作者归属正确。
2. 重复消费按次扣点；一次解锁换设备恢复且不重复扣；按期权益延长/到期正确；订阅授权、周期扣点、取消和余额不足分支可验证。
3. 并发消费、双击、重复回调、价格更改、浏览器关闭、断网与 Worker 中断均不重复扣点、不出现负余额、未扣点授予权益或已扣点无可恢复交付。
4. 另一 appId/origin/item、伪造价格、越权退款、通用云数据写入、伪造 postMessage 不得改钱包或他人权益；已有免费部署与 SDK 登录/云存储不退化。
5. 受控 AI 服务有输入/输出预算和可信结果，明确失败释放预留，unknown 恢复不重复调用/收费；确认成本与作者收入可对账。
6. 真钱充值的渠道通知重放只入账一次，退款/拒付与原批次、权益和作者收入一致；作者实际结算到账与渠道账单一致。没有这个证据不能称收费闭环上线。
