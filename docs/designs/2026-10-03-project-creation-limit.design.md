# 每日新增应用的轻量限制

用户于 2026-10-03 要求防止同一账号大量刷应用，同时明确“千万不要过度限制”“初步简单限制”。按项目全托管授权实现、验证、上线。flow=standard，风险 L3 / 发布 L4；单批闭环，plan=not-required。

## 调查与选择

当前没有账号每日新增或部署次数额度；网页 draft 和 CLI/classic 创建最终都写入 API Worker 的 projectRepository.createProjectRecord。Node builder 没有项目创建路由，只承接已有项目部署。最近 14 个北京时间自然日，单账号单日最多 16 个新项目（含草稿及软删除）；20 个上限未命中任何历史账号日。

| 方案 | 影响与成本 | 选择 |
| --- | --- | --- |
| 每日部署次数限制 | 正常调试、重试与旧应用更新都会占额度，不能直接治理列表新增 | 不采用 |
| 每日新增应用 20 个，旧应用更新不占额度 | 针对新增刷量，复用创建记录和统一写入口，无额度表 | 采用 |
| 指纹去重、积分、分级/IP 限流 | 需要另定义相似度和例外，会扩大误伤及实现范围 | 不纳入用户要求的初步简单限制 |

## 冻结行为与 owner

- 每个已登录账号每天最多新增 20 个应用，北京时间 00:00 重置。私有、草稿、软删除项目都计数；删除不能返还额度。创建失败未写入不扣额度。
- 旧项目更新、重新部署、已有草稿重试不创建记录，不占新增额度。本次不添加每日部署次数上限。
- 创建事实与原子保护归 projectRepository；INSERT 与当前日 COUNT 在同一 SQL 语句决定，避免并发先查后写超额。统一 repository 捕获创建时刻，同时用于 created_at 与日期窗口，避免 AI 等待跨日错桶。索引 owner_id,created_at 在旧字段补齐后创建。
- Service 在元数据生成/地址分配前做快速额度检查；最终 INSERT 再检查是并发正确性保护，不产生第二份计数状态。所有正常创建入口 requireAuth，owner 从认证会话获得，不能从请求 body 更改。
- 达限返回 HTTP 429、稳定 code=DAILY_PROJECT_LIMIT、limit 和 resetAt；CLI 使用英文 error 提示，网页按语言显示“今天新增已达 20 个（含草稿），可更新已有应用，次日北京时间零点恢复”。保留已输入内容和最近应用入口。
- 复用原有创建、更新、错误显示链路；通用项目请求错误解码从地址专用文件移动到请求错误文件，保留现有地址错误行为。无新额度接口、计数表、套餐或部署限制。

## 方案 Review

独立反查用户“简单、宽松”要求与网页/CLI入口：20 高于近期最高 16；新增事实复用现有记录；原子写保护覆盖并发；不限制旧应用部署；软删除不返额度；所有创建路径 owner 来自认证。无开放 finding，design-review=passed。维护性审计：一个 quota helper 拥有数值与日历，repository 拥有计数和写入；错误传输字段均有现用消费者。无需增建通用限流基础设施。
