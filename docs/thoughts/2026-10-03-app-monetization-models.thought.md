# GemiGo：结合应用形态探索变现与收费模式

日期：2026-10-03（Asia/Shanghai）

背景：[当前能力与定位边界](2026-10-03-app-deployment-direction.thought.md)、[现有应用分析](2026-10-03-app-portfolio-analysis.thought.md)、[创作者收入激励思路](2026-10-03-creator-inspiration-and-distribution.thought.md#用户新增思路作者收入驱动创作与主动传播)。

## 用户纠正与目标

用户明确指出：“不是作者发布商品，咱们不是发布商品……要考虑咱们这种应用形态通常可以用哪些变现的方式，或者哪些收费的模式。”

因此，研究从应用的实际使用方式开始：用户打开、游玩、学习或完成工具任务时，哪些价值能够形成收入，以及平台怎样支持并参与分成。AI 先前把分成需求收窄为作者销售作品的默认建议已撤回，[原设计入口](../designs/2026-10-03-creator-commerce.design.md)已标记失效。

仍保留用户的机制假设：降低开发门槛，帮助作者获得可验证的收入，让作者自身收益推动宣传、迭代和持续创作。广告主、应用使用者、赞助方均可能是收入来源；收入分成不要求所有收入都来自消费者购买作品。

## 与现有应用对应的候选

下表是 AI 基于现有应用内容提出的适配判断，未证明当前作品有付费意愿、广告收益或留存。

| 模式 | 应用内的收入触发 | 对应现有形态与例子 | 技术接入与主要限制 |
| --- | --- | --- | --- |
| 广告收入分成 | 用户免费使用，广告渠道产生有效收益，平台与作者按规则分配 | 轻游戏、兴趣问答、知识探索、查询工具；适合研究作者推广带来更多有效使用的机制 | 页面广告可研究平台辅助接入；关卡间插屏、激励广告需要应用告诉平台何时暂停、完成观看和恢复。收益依广告渠道确认，不能按平台 PV 自行造收入；渠道准入、填充与实际规模待核实 |
| 自愿打赏/支持作者 | 使用后选择支付，不改变原有免费功能 | 有趣的小作品、实用工具、创意展示、知识互动页 | 平台可研究统一支持入口，核心应用少改或不改；仅链接作者外部收款不能自动实现平台分成，内置分润仍需获准渠道。付款率与稳定收入待验证 |
| 一次性付费功能/应用内解锁 | 免费基础体验后，支付解锁额外功能或内容 | 跑酷工坊类关卡编辑器的高级能力、工具的批量处理/导出、学习应用的拓展练习，均为功能假设 | 应用需要声明具体能力并接入权益检查；后台控制受保护数据或服务。纯前端隐藏按钮无法可靠保护已经公开交付的程序；是否值得为纯静态内容做访问保护须另行判断 |
| 订阅 | 为持续价值按周期支付 | 经常使用的工具、持续练习/更新的学习应用、具备长期数据服务的应用 | 登录、订阅状态、到期/取消/续费失败与后台权益；单个一次性小游戏不能仅凭题材证明适合订阅。单应用与平台会员是不同选择，后者分配收入需另定规则 |
| 按次数、额度或结果付费 | 免费试用后，为下一次服务或结果支付 | AI 问答、生成、分析、报告等候选应用；不表示现有目录已有稳定此类服务 | 后台执行、可靠计量、额度预占/核销、失败回补、幂等与成本控制。不能按用户点击或前端自报次数收费；按结果需定义成功/失败，按调用需说明实际扣费口径 |
| 赞助/推广/有效转化佣金 | 品牌赞助体验，或应用带来可核对的商业转化 | 垂直知识体验、活动互动、特定查询或推荐工具 | 需具体赞助方或合作渠道，归因与确认佣金；商业相关性是前提。尚未形成招募、联系或推广授权 |

上述例子只表达模式对应，未授权改变这些作者的作品，不把已有作者当作已同意变现或分成。

## 三个具体应用故事（均为候选）

- 轻游戏照常免费运行，在用户主动选择的合适环节展示广告；广告渠道确认收入后作者分润。作者增加有效游玩可能增加收入，消费者不必先购买应用。学习作品是否适合广告、展示频次及受众体验要单独判断。
- 工具保留免费基础功能，用户完成日常任务后可选择付费高级导出或批量处理；同一应用内继续使用，平台确认支付与功能权限，作者获得收入。
- AI 应用允许试用，之后用户购买指定次数或服务额度；服务端完成请求并按明确规则核销，扣除约定服务成本后确认作者与平台份额。收费规则不能让作者无限消耗平台模型成本。

当前不能从“应用免费可用”推出广告优先，也不能从“需要收费能力”推出付费功能优先。需先找实际应用、使用时机和收入来源。

## 技术层面的不同接入深度

**平台可辅助的外层能力：**作者收益设置、支持入口、经授权的页面广告位、收入与结算展示。现有网关有 HTML 处理机制，可作为调查起点；任意页面的 CSP、布局、iframe、脚本冲突和作者选择仍需验证，不能承诺所有应用自动兼容。

**应用需要配合的内部能力：**插屏时机、激励广告奖励、具体高级功能解锁、额度消耗和结果交付。适合探索模板或窄 SDK 接口，让 AI 生成的应用容易接入；平台不自动猜测一份 HTML 的关卡、付费功能或计费事件。SDK 名称与合同尚未设计，不先冻结通用 monetization 框架。

**必须有可信后台的能力：**支付确认、权益、真实服务调用与计量、广告收入导入/对账、作者归属、分成与结算。收入应稳定关联到应用与作者；平台访问统计用于分析使用，不能充当支付或广告结算凭证。

## 外部机制参考与证据边界

2026-10-03 查阅官方资料：

- [Google Ad Placement API](https://developers.google.com/ad-placement)支持 HTML5 游戏/互动内容的插屏和激励广告；[运行结构说明](https://developers.google.com/ad-placement/docs/html5-game-structure)要求广告标签与 API 在游戏文档内，不能假设宿主页面统一插入即可控制 iframe 内任意玩法。文档提供机制证据，不代表 GemiGo 已获准接入或会有收益。
- [AdSense for Platforms](https://developers.google.com/adsense/platforms)展示平台与用户广告收入分配及渠道付款机制，是企业级产品，有申请入口；不能把“有分成 API”当成当前小规模项目已可开通，也不能自动推断它与游戏广告产品可组合接入。
- [itch.io HTML5 托管说明](https://itch.io/docs/creators/html5)允许 HTML/JS/CSS 应用在浏览器运行，其 HTML5 类型目前接受捐赠。它提供“免费运行＋自愿支持”的参考，不证明 GemiGo 作者将获得稳定收入。
- [Stripe 按量计费说明](https://docs.stripe.com/billing/subscriptions/usage-based)提供使用量收费机制参考；GemiGo 自身的服务计量、执行、成本与渠道准入仍需另行设计，不默认采用该服务商。

## 下一步判断与升级条件

建议拿少量真实应用比较：是否重复使用、哪个环节产生价值、谁付款或赞助、作者需要怎样接入，以及平台和作者的实际成本。对广告研究有效使用量、渠道准入与收入；对付费功能研究具体购买意愿；对按量收费研究可信执行与成本。当前访问规模不支持稳定广告收入预测。

有具体应用和收入触发之后，再确定作者开通方式、使用者操作、可信后台 owner、归属/分成规则与可执行验收，升级成该模式的正式技术设计。支付主体调查按选中模式推进，不能替代这一层适配判断。当前仅修正记录与研究候选，无模式已选定或功能已上线。
