# GemiGo 统一点数：实施顺序

日期：2026-10-04（Asia/Shanghai）
状态：落地准备方案；当前没有产品源码实现或生产迁移。平台内顺序已明确，服务执行和真实支付部分需完成各自输入门。
上位：[统一点数设计](../designs/2026-10-04-platform-points.design.md)。active-contract=`gemigo-platform-points-design-20261004`，scope-revision=1；本次方案交付标准由设计中的 PPD-01～05 唯一维护。

## 执行部分与依赖

| 部分 | owner 与输入 | 交付结果 | 设计策略与进入门 |
| --- | --- | --- | --- |
| W01：账户、账目与收费项 | API Worker；稳定 user/project/author 与隔离测试库 | 迁移、收费项 CRUD、来源批次、钱包流水、收据和原子权益/额度授予 | 复用上位结构；首个源码修改前补精确 schema/API，先以本地 D1 验证原子状态链、余额不足、并发和幂等 |
| W02：平台确认与作者入口 | frontend；W01 | 作品设置“点数与收益”、平台钱包与消费窗口、隔离测试充值入口、消费/退款记录 | 复用上位用户链路；补具体页面状态、移动回跳及平台会话/CSRF；测试点不进入生产可提现收入 |
| W03：SDK 与非 AI 试点 | app-sdk、API、两个平台自制或获授权应用；W01/W02 | 收费项读取、purchase、收据/权益查询、额度核销；真实应用内按次与一次自定义触发 | 复用上位协议；收费点由作者逻辑决定，SDK 接入示例与创作提示词随实现更新。具体试点需有权限，不直接修改用户作品 |
| W04：按期权益与订阅周期 | API 与 frontend；W03 | 手动按期购买及延长、明确续费授权、周期唯一扣点、取消、余额不足与到期、收入快照 | 复用 term 模型；先补调度/幂等 SQL 及授权 UI，手动买按期权益不代替自动续费验收 |
| W05：受控服务与 AI 试点 | API/受控上游；W03 | 预留→执行→持久结果→结算、失败释放、unknown 恢复；一个 AI 服务应用 | 开始前细化设计：固定服务、成本预算、模型和上游幂等/查询合同，核查既有代理消费者与绕过路径。不能用 cloud.ping 或 stub 替代真实服务 |
| W06：真钱充值与作者结算 | 唯一批准渠道；W01～03 和主体/地区信息 | 真实充值、验签/查单/对账、资金来源退款、作者收款入驻与结算 | 支付渠道确定后补独立支付专题设计与正式 Review，确认统一充值跨应用消费及第三方作者结算准入；测试余额不能当作本部分完成 |
| W07：按批组装与线上验收 | 本批触达的 API、frontend、SDK 与试点部署 | 两个以上应用同钱包消费、作者收入、退款和真实到账的证据；后续批次追加按期/续费和 AI 验收 | 按上位候选验收建立各批产品实施 active ledger，定向验证、diff-only Review、精确提交/普通推送/本地主线同步与适用部署；每批如实限定已支持类型 |

第一批为 W01→W02→W03，加上 W06 后执行 W07，覆盖按次/一次、两个非 AI 应用、共享余额、真实充值及作者到账。W06 的主体和渠道调查与平台内部分并行推进；不是等主体明确后才开始设计，也不必等 W04/W05 才上线第一批。第二批推进 W04，W05 可独立推进，各自完成后再次按 W07 验收。平台机制验证成功不能替代真钱与作者到账，第一批成功也不能宣称订阅或 AI 已支持。

## 必须传播的公开合同

| 合同 | producer → 必须触达的 consumer |
| --- | --- |
| 收费项 repeatable/durable/term | 作者设置 → API 校验与存储 → 消费快照 → 权益/续费 → SDK 类型与运行 → 作者/用户界面 |
| 消费结果 granted/pending/cancelled 与错误 | 交易服务 → API 响应 → SDK 序列化/导出 → 平台窗口回传与恢复 → 应用示例和创作提示词 |
| 点数接口 | `types/points.ts` → `GemigoSDK`/公共导出 → `apis/index.ts` 直接 web 模块 → 发布包/托管入口 → 实际应用；非浏览器宿主明确支持边界 |
| 项目身份与权益 | 作品 owner/id/origin → 消费意图 → 平台账号与 SDK appUser 映射 → 同 app 的读取/核销；域名更新不迁移财务归属 |

不建立新的能力目录或宿主 RPC 通用层；先沿已有 auth/cloud 直接 web 接入方式完成对应消费者。旧版本 SDK 在未接入变现的应用仍可用，收费应用必须使用含点数接口的版本，不静默用旧 stub 假装成功。

## 验证、Review 与交付

源码实施按最窄受影响包进行 TypeScript 检查、targeted lint 和定向测试。金融状态测试必须覆盖 D1 组装边界，UI/SDK 验收从真实应用点击进入平台确认再返回，后台直调不能替代应用接入。SDK 类型通过后仍需构建并加载实际包，已有 auth/cloud 回归。

每部分的有效设计先完成 mode=design Review；源码验证后完成 diff-only 可维护性检查与 implementation Review，有 finding 回到对应部分修复。真实渠道审核、充值/结算、迁移和发布结果分别留证；线上验收不得混用 test/live 记录。

## 恢复入口与未决输入

本文件为当前方案阶段唯一执行顺序入口，设计持有合同、结构与状态语义。执行启动时按项目规范创建任务日志，记录采用设计版本、产品 active ledger、当前部分、证据及未关闭项；跨批恢复先查日志，不从最新 Git 提交猜完成。
